## What the codebase does

This library rewrites SPARQL 1.2 queries (which may contain triple-term / RDF-star patterns) into equivalent SPARQL 1.1 queries executable against RDF 1.1 data sources. Mappings are expressed as SPARQL CONSTRUCT queries; the library unfolds each BGP triple pattern into a UNION of subselects, one per mapping.

## What happened with GROUP BY in user queries (the bug)

**Before the fix**, a user query like:
```sparql
SELECT ?s (COUNT(?o) AS ?count) WHERE { ?s ?p ?o } GROUP BY ?s
```
produced **invalid SPARQL**:
```sparql
SELECT ( ?uq_s AS ?s ) ( ?uq_count AS ?count ) WHERE {
  { SELECT ?m0_o ?m0_p ?m0_s WHERE { ?m0_s ?m0_p ?m0_o . FILTER(!ISTRIPLE(?m0_o)) } }
  BIND( ?m0_o AS ?uq_o )
  BIND( COUNT( ?uq_o ) AS ?uq_count )   ← INVALID: aggregate in BIND
}
GROUP BY ?uq_s
```

**Root cause**: `queryTransform` strips the outer `Project` and adds *outer* `Extend` rename nodes (mapping original variable names back from `uq_`-prefixed ones). The `toAst` engine (`translateAlgProject`) flattens *all* visible `Extend` nodes, calls `replaceAlgAggregatorVariables` to substitute the intermediate aggregate variable (e.g. `uq_var0 → COUNT(uq_o)`), and then `putExtensionsInGroup` dumps any unconsumed `Extend` directly into the WHERE clause — producing `BIND(COUNT(...) AS ?uq_count)`.

---

## The fix (`lib/transformBgp.ts`)

Added `hasGroupInTopLevelChain()` which traverses the `Extend` / `Filter` / `OrderBy` chain to detect a `Group` node.

When the user query has GROUP BY, **before** adding the outer rename `Extend` nodes, the transformed algebra is wrapped in a `Project` (subSELECT) projecting the `uq_`-prefixed result variables. This isolates the aggregate structure so `toAst` serialises it correctly as a nested subquery:

```sparql
SELECT ( ?uq_s AS ?s ) ( ?uq_count AS ?count ) WHERE {
  SELECT ?uq_s ( COUNT( ?uq_o ) AS ?uq_count ) WHERE {
    { SELECT ?m0_o ?m0_p ?m0_s WHERE { ?m0_s ?m0_p ?m0_o . FILTER(!ISTRIPLE(?m0_o)) } }
    BIND( ?m0_o AS ?uq_o )
    BIND( ?m0_s AS ?uq_s )
  }
  GROUP BY ?uq_s
}
```

**Covered cases**: simple GROUP BY, multiple projected vars, HAVING, ORDER BY, DISTINCT+GROUP BY, unprojected group variable, multiple aggregates, combined with substitution optimisations.
